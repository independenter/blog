救急

现场救火：在崩溃边缘抢回系统

🔥

千亿级三级缓存架构 OOM

情况：现场数据量巨大，系统频繁崩溃

介入：Dump 堆内存 → 分析 Ehcache 对象 → 定位 LRU 配置层级失控

结果：配置 net.sf.ehcache.use.classic.lru=true，永久解决一级缓存问题

💾

Metaspace 溢出：微服务稳定性危机

情况：新同事自研 RPC 框架，注解生成大量动态代理类

介入：Dump 元数据空间 → 梳理动态代理类 → 估算实际内存需求（128M → 512M）

结果：程序稳定运行 5 年未再发生此类问题

⚡

CPU 占用过高：微服务环路调用

情况：新功能部署后，某时间段 CPU 持续飙高

介入：top -H 定位线程 → jstack 分析调用链 → 发现服务间环路调用

结果：拆解环路，恢复系统稳定性

🗄️

MySQL 持续崩溃：慢 SQL + 连接风暴

情况：索引选择性极低 + 应用层假慢查询 + 微服务连接线程吃光内存

介入：优化索引 → 限制查询数据量 → 调整连接池配置

结果：数据库恢复稳定，支撑业务持续增长

🔐

Kafka + SASL_SSL 通信排查

方法：OpenSSL 获取服务端证书 → JDB 监控关键返回 → 确认环境匹配

📊

Kafka 生产消费速率不匹配

方法

04 / METHOD · 从问题到上线，4—8 周
  1. 01

    先问清楚问题

    不急着画界面。用访谈、观察和已有数据确认：谁在什么场景下卡住，卡在哪一步，现在怎么绕过。把「我想要一个功能」翻译成「我想要一个结果」。

    访谈 · 观察 · 数据
  2. 02

    用最粗的笔画流程

    先在纸上排结构：一屏先放什么、后放什么、哪一步可以删掉。线框只验证顺序与密度，不提前讨论阴影和圆角。

    信息架构 · 线框
  3. 03

    把设计写进代码

    能自己实现的部分自己做。使用真实内容、真实长度和真实边界做界面，提前暴露那些只在交接时才会出现的问题。

    原型 · 前端 · 可用性测试
  4. 04

    上线之后继续

    上线不是交付终点。看真实使用路径，按周做小改动；用数据修正直觉，也用直觉判断哪些数据不该被追。

    观测 · 迭代 · 复盘
